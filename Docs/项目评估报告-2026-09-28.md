## 1. 总体判断

**这个项目具备继续投入的价值，适合作为 ARPG 开发底座和玩法原型。当前最需要投入的是交付可靠性、状态一致性和回归验证。**

项目已经把能力系统、背包装备、任务对话、UI、输入设置和多种玩法组织起来，避免了所有逻辑都集中在主模块里的问题。CommonGame、CommonUI、Game Features 和 GAS 的使用也为后续扩展留下了空间。

但现有工程还不足以证明自己是“换一台机器即可重建、改动后能自动验证、联机和存档行为稳定”的成熟模板。核心插件没有随主仓库交付；代码中有可定位的状态错误；编辑器日志显示部分 GameplayTag 已经与资产脱节。这些问题会直接影响后续开发效率和行为可信度。

建议先用一个完整流程作为收敛目标：**进入游戏 → 战斗 → 获得物品 → 换装 → 更新任务 → 存档 → 重启恢复**。把这个流程在目标运行模式下验证稳定，再扩展武器、玩法和在线平台。

## 3. 项目优点

### 3.1 分层方向合理，主工程没有承担全部业务

`Template` 主模块很薄，玩法分别放在 ARPG、SideScroller 等 Game Feature 中，ARPGUI 承担界面内容，RPGCore 汇聚公共能力。对于复用角色、物品和 UI 逻辑，这种组织方式比在单个游戏模块中不断堆叠功能更易管理。

需要保留这个方向，同时明确边界。RPGCore 目前依赖 GAS、背包、UI、Mass、对话和技能树，通用核心的实际依赖面仍然较宽。可从 [RPGCore 插件声明](G:/Template/Plugins/RPGCore/RPGCore.uplugin:24) 和 [模块依赖](G:/Template/Plugins/RPGCore/Source/RPGCoreRuntime/RPGCoreRuntime.Build.cs:25) 查看。

### 3.2 联机实现已经考虑了部分关键生命周期

PlayerState 中的 AbilitySystemComponent 开启复制，并采用 Mixed 模式。背包管理器在服务器创建实例，处理客户端对象尚未到达的情况，也包含子对象注册和注销逻辑。这些都是后续验证联机行为时可利用的基础，不需要整体推倒重做。

证据：[RPGPlayerState](G:/Template/Plugins/RPGCore/Source/RPGCoreRuntime/Private/Gameplay/RPGPlayerState.cpp:19)、[背包初始化](G:/Template/Plugins/RPGInventorySystem/Source/RPGInventorySystem/Private/Inventory/RPGInventoryManager.cpp:27)、[背包复制准备](G:/Template/Plugins/RPGInventorySystem/Source/RPGInventorySystem/Private/Inventory/RPGInventoryManager.cpp:417)。后两个文件属于本地被忽略的依赖，应先解决其版本管理。

UI 通过 Game Feature Action、Layer、Slot 和 UIExtension 组织，动作类已经检查空 WidgetClass、无效 LayerID 和 SlotID。这比完全依赖人工配置更稳妥，后续可以把相同做法推广到物品、技能和任务数据。

### F02 · 新任务忽略传入状态，通知与真实数据不一致｜P1｜已确认代码缺陷

`AddQuest(QuestName, State)` 将参数传入列表，并用该参数广播 `OnQuestAdd`。但 `FQuestList::AddEntry` 把 `NewEntry.State` 固定赋为 `0`。

例如调用 `AddQuest("Quest_A", 2)`，服务端添加通知中的状态是 2，列表查询得到的状态却是 0，复制后的客户端也依据列表接收 0。这会影响任务恢复、分支任务和 UI 显示。

建议保存传入的 `State`，并统一使用实际写入的条目生成通知。

**验收：**分别以 0、1、2 初始化任务；即时查询、服务端通知、客户端复制通知和稍后加入客户端看到的状态全部一致。

证据：[添加接口](G:/Template/Plugins/DialogStateTree/Source/DialogStateTree/Private/Quest/QuestComponent.cpp:17)、[错误赋值](G:/Template/Plugins/DialogStateTree/Source/DialogStateTree/Private/Quest/QuestComponent.cpp:120)。

### F03 · 任务变更接口缺少统一的权威判断和成功语义｜P1（联机场景）｜已确认接口缺口

`ChangeQuestState` 没有 `BlueprintAuthorityOnly`，函数内部也没有服务器权限判断，客户端可以走入本地修改和广播。这里不能据此认定客户端能够改变服务器状态；直接可见的风险是客户端状态、事件与服务器权威数据不一致。

此外，重复添加没有查重；修改不存在的任务仍广播“已改变”；删除不存在的任务仍广播“已删除”。上层 UI 或任务奖励若只监听事件，可能收到与真实列表不对应的通知，具体调用路径仍需检查蓝图。

建议所有写接口在运行时统一判断 authority，并返回明确结果；只在实际成功变更后广播。定义重复任务是拒绝、幂等返回还是更新，避免不同调用方各自理解。确需客户端请求时，再增加带校验的服务器请求路径。

**验收：**覆盖重复添加、缺失任务修改/删除、客户端直接调用；失败操作不改变数据，也不发出成功通知。

证据：[接口声明](G:/Template/Plugins/DialogStateTree/Source/DialogStateTree/Public/Quest/QuestComponent.h:110)、[修改与通知](G:/Template/Plugins/DialogStateTree/Source/DialogStateTree/Private/Quest/QuestComponent.cpp:23)、[列表写入](G:/Template/Plugins/DialogStateTree/Source/DialogStateTree/Private/Quest/QuestComponent.cpp:108)。

### F04 · 存档子系统默认持有共享类默认对象｜P1｜已确认实现，影响取决于调用路径

`UGeneralSaveSubsystem::Initialize` 使用 `SaveGameClass.GetDefaultObject()` 作为 `SaveData`，而 `GetSave` 返回该对象的可变指针。类默认对象（CDO）不是每个 GameInstance 独立创建的运行时存档。

如果调用方在执行 `SetSaveGame` 替换它之前写入存档，就会修改共享默认对象；同进程多实例、再次进入 PIE 或切换存档槽时存在状态串用风险。尚未检查所有蓝图调用，不能断言实际存档已经损坏。

建议通过 `CreateSaveGameObject` 或合适 Outer 的 `NewObject` 创建独立实例，只将 CDO 用作默认值来源。明确“新游戏、读档、换槽、退出”的对象生命周期，并在可见存档结构中补充版本和迁移约定。

**验收：**两个 GameInstance 默认持有不同对象；修改其中一个不改变另一个及 CDO；新游戏、换槽和重新进入 PIE 均能得到预期状态。

证据：[共享对象赋值](G:/Template/Plugins/GeneralSystemSetting/Source/GeneralSystemSetting/Private/System/GeneralSaveSubsystem.cpp:23)。该文件属于主仓库忽略的本地依赖。

### F05 · 物理与魔法伤害缺少穿透率边界处理｜P1｜已确认边界缺口

两条执行路径均将 `Defense × (1 − Penetrated)` 用作分母。代码只处理 `Defense == 0`，没有处理穿透率等于 1、超过 1、负防御或非有限输入；所检查的属性类也没有对穿透率实施边界限制。

穿透率等于 1 时分母为 0，超过 1 时分母为负。物理路径之后限制到 1～99999，魔法路径直接取整；因此相同的边界配置可能产生不同且不符合设计的结果。实际资产是否能达到这些值尚未验证，但执行层缺少保护可以直接确认。

建议先定义穿透率合法范围和 100% 穿透的语义，再统一处理有效防御、属性捕获失败和非有限结果。若允许完全穿透，应明确其伤害规则，避免只加一个极小分母掩盖设计问题。物理伤害最小为 1 是否有意设计，也应写入数值约定。

**验收：**覆盖穿透率 0、0.5、0.99、1、1.2，防御 0、正数、负数及缺失属性；输出有限，并符合物理、魔法各自明确的设计规则。

证据：[物理伤害公式](G:/Template/Plugins/AdvancedGASSystem/Source/AdvancedGASSystem/Private/AbilitySystem/Abilities/Executions/RPGDamageExecution.cpp:63)、[魔法伤害公式](G:/Template/Plugins/AdvancedGASSystem/Source/AdvancedGASSystem/Private/AbilitySystem/Abilities/Executions/RPGMageExecution.cpp:64)。两者均属于被忽略的本地依赖。

### F07 · UI 添加状态的作用域过大｜P2｜条件触发的代码风险

**2026-09-28 修复记录：已完成代码修复，运行验收待执行。** 已移除 Action 级 `bIsAdd`，改为按 Context/HUD 保存独立状态；统一移除布局和扩展；停用时先移除上下文，防止迟到回调重建状态；处理 UI 创建期间发生移除的情况，并补齐 Layout 的 Client 资源包登记。保留原有 `AddWidgets` 事件触发时机。修改的 C++ 文件已使用本机 UE 5.8 工程编译参数完成独立编译，相关差异检查通过；没有执行完整链接或 PIE 测试，正在运行的编辑器仍使用原模块。以下保留评估时的原始发现。

`UGameFeatureAction_AddWidgets` 已经按 Context、HUD 保存数据，却另用一个动作对象级别的 `bIsAdd` 阻止重复添加。第一次添加后，同一个动作对象为第二个 HUD 添加 UI 会直接返回；移除任意 HUD 又会把全局标记清掉。

在同一动作服务多个本地玩家、多个上下文或 HUD 切换重叠时，这个标记与真正的 UI 所属对象不一致。不能据此认定所有多人客户端都会缺 UI，触发前提是它们共享同一个 Action 实例。

建议将幂等判断放在 `FPerActorData` 内，按 Context 和 HUD 判断是否添加成功；只清理对应对象的数据。同步验证 Feature 停用、重启和 UI 重建。

**验收：**两个本地玩家各有一套 UI；移除一个不影响另一个；重复添加不重复堆叠；停用再启用能恢复。

证据：[共享标记](G:/Template/Plugins/RPGCore/Source/RPGCoreRuntime/Public/GameFeatures/GameFeatureAction_AddWidget.h:104)、[添加入口](G:/Template/Plugins/RPGCore/Source/RPGCoreRuntime/Private/GameFeatures/GameFeatureAction_AddWidget.cpp:139)、[移除入口](G:/Template/Plugins/RPGCore/Source/RPGCoreRuntime/Private/GameFeatures/GameFeatureAction_AddWidget.cpp:175)。

### F08 · 网络配置中有明确键名错误，后端组合需要实际验收｜P2｜部分已确认，部分待验证

基础配置写的是 `+NetDriverDefinition=`，本机 UE 5.8 引擎对应的配置属性为 `NetDriverDefinitions`。这条配置不能按预期加入引擎的驱动定义数组。CustomConfig 中的 Steam/EOS 覆盖使用了正确的复数键，因此不能推断所有构建目标都受同样影响。

此外，若干 Iris 过滤与压缩条目有多余右括号，需要用实际解析结果核对；`SteamDevAppId=480` 和 EOS 注释占位值表明在线配置还不是可直接验收的正式环境配置。不要把“文件中声明了 Iris/Steam/EOS”视为相应联机路径已经生效。

建议修正基础键名，清理配置格式；每个目标记录实际加载的服务、NetDriver 类型及复制模式。先稳定一个主要后端，再扩大组合矩阵。若计划 Linux 专用服务器，还需核查插件平台限制，例如 AdvancedGASSystem 当前模块白名单未包含 Linux。

**验收：**目标构建启动日志显示预期驱动和后端；至少两个客户端完成连接、加入、离开、重连及物品/任务状态同步；分别记录 Listen Server 与 Dedicated Server 的结果。

## 6. 推荐实施顺序

### 第一阶段：修正状态和数据问题

优先处理 F02 任务初始化、F04 存档对象和 F05 伤害边界；联机是目标时同步处理 F03。修复 F09 的空指针入口，并逐项清理 F06 的业务 Tag 警告。

每个修复都附上能失败、能通过的回归场景。此阶段的完成标准是数据与通知一致、状态相互隔离、非法输入结果明确，而不是只让编辑器不显示报错。

### 第二阶段：让工程能够重复交付

处理 F01 的依赖版本和恢复流程，收齐计划交付的 Target/CustomConfig，修正 F08，完善 F11 的跟踪规则和 F12 的快速开始。随后在新目录执行一次完整恢复与构建，保留日志和产物标识。

同时落地 F10 的最小自动化入口：先覆盖已经修复的缺陷，再扩展到业务资产和关键地图。不要一开始追求宽泛的覆盖率数字。

### 第三阶段：验收完整流程，再做优化

完成下面的验收矩阵后，处理 F07 多上下文 UI 生命周期，建立性能与包体基线。根据数据决定是否拆分插件、减少依赖、调整渲染档位或裁剪素材。

如果目标仅为单机，可暂缓在线后端矩阵和多人 UI 场景，把资源投入存档、战斗与内容制作；如果目标是可复用联机模板，则联机矩阵必须成为交付条件。
